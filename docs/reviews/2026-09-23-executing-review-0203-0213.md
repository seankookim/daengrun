### F2 · medium · `0203_availability_exceptions.sql` §1 + `app/app/runner-profile/[id].tsx:174` + `app/app/owner/reschedule.tsx:131`
**The 추가 근무 (`extra`) row is honoured by the server and cannot be offered by any owner-facing

② 18:00 outside the grid, no extra                  -> f   (control)
③ 18:00 WITH an extra 18:00-20:00 on that date      -> t

  (`app/src/lib/api.ts:2569` `fetchRunnerAvailability`, `app/src/lib/api.ts:3221` inside

So for an `extra` window `daySlots` is EMPTY and `checkSlot` is never even called — the server's

「휴가는 그 기간의 예약을 막고, **추가 근무는 그날 그 시간만 엽니다**」.

shipping the 추가 근무 affordance with that copy.** Fix is client-side (the slot sheet must union
`extra` windows into its candidates for the selected date) or copy-side; no migration is needed.

⚠ Related and MEASURED with a control, stated so it is not rediscovered: the 휴가 does **not**

overstates it: a 휴가 removes the SCHEDULED offer and leaves the 지명 and find-now offers standing.

### F3 · medium · `0208_ops_roster.sql:231-337`
**`payout_due` is effectively root, and the slice never says so.**

MEASURED, as an active `payout_due` operator, with every other `payout_due` row neutralised so no
guard could be masking the result:

```
=== H-1: does the door care what the target IS? ===
target xrev_nobody: 0 booking(s), runners row? f
seat a NON-party in payout_due -> changed=t active=t
  ops_me() for that person now: is_ops=t

=== H-2: can an operator add THEMSELVES to a class they do not hold? ===
before: op1 in return_strand? f
self-seat in return_strand -> changed=t
after : op1 in return_strand? t   (ops_resolve_return_tx / ops_stranded_returns now open)

=== H-3: can an operator REMOVE a different operator? ===
deactivate the OTHER payout_due operator -> changed=t active=f
```

So one seated operator can (a) hand `is_ops` — and with it `ops_bank_account`, which decrypts a
runner's account number (0194 → 0202) — to any non-tombstoned profile, including one that has never
been a party to anything; (b) grant themselves `return_strand`, which is the gate on
`ops_resolve_return_tx`, a door that seals and SETTLES a booking; (c) deactivate any other operator
while one remains. The thirteen classes are a routing vocabulary, not a privilege separation.

The two guards that ARE there work, measured:

```
active payout_due operators: 1 (the caller is the only one)
H-4 self-deactivation as THE LAST operator -> last_operator  (guard present)
   rows unchanged? active payout_due count is still 1
```

and `ops_roster_changes` recorded all four of my writes with the actor, which is what makes this
auditable rather than silent.

**Does not block the push.** For a one-operator pilot it is defensible and the journal is the right
mitigation. But `§0b`/`§0d` argue the class gate at length and never state that **the door can
grant its own class**, and that should be Sean's explicit call rather than an emergent property of
「one class constant, one window」. **Correct-forward (0214+, or prose in the next roster slice):**
either state it in the header and the console copy, or separate 「seat an operator in `payout_due`」
from the other twelve classes.
