## 2. The eight collisions, and the arc

Ordered as they happened:

1. **0078 ×3** — three sessions, three files, one number.
2. **0081 ×2** — same shape, one hour later.
3. **`/tmp/dr85` ×2** — two sessions derived a *temp harness directory* from the migration
   number, and deleted each other's postmaster mid-run. It presents as a migration file
   vanishing during an apply: it looks exactly like disk corruption.
4. **0082 ×2** — number claimed while another session's build agent was mid-write.
5. **0083 ×2 (the double-yield)** — both sessions politely yielded the number to the other and
   both moved to 0084. *Deference produced its own collision.*
6. **0086 — a pushed FILE with no ledger ROW.** The rule said "a number is claimed when it's on
   origin", and the file WAS on origin — only the row wasn't. A newly-started session was told
   0086 was free.
7. **0089 ×2 — rows with no files.** The exact inverse of #6, and the pre-push hook is
   structurally blind to it: the hook refuses a push that *introduces* a colliding number, and
   neither file had been pushed.
8. **`pkill -f postgres` matched SEVEN processes.** `harness.sh` exported a *relative*
   `PGDATA=./.pgtest/data`, so every session's postgres command line was byte-identical. One
   session clearing its own stale postmaster killed everyone's.

**Is the "sessions racing → automating the referee → no identifier at all" arc real?**
**No — and this document asserted it before checking.** An adversarial pass over the timestamps
refuted it, and I verified the decisive ones myself:

| event | time |
|---|---|
| the auto-resolver silently deleted a live `0087` claim (`15846e3`) | **15:23:09** |
| the pre-push hook was created (`3fcfeb8`) | **15:31:40** |

**The resolver ate the claim eight minutes and thirty-one seconds BEFORE the hook existed.** So
"a guard on one step invites delegation of the next" — which the first version of this retro
called *the sharpest predictive line the day produced* — describes a psychology that had not yet
had time to exist. The resolver was **pre-existing merge automation**, already mangling
`REGISTRY.md` at `96fd09f` (15:20:47), because that file had become the most conflict-prone in
the repo *precisely because five sessions were racing to append rows to it.* That is leg one
continuing onto a new surface, not a new stage.

**And the third leg is the day's OLDEST cause, not its newest.** The duplicated ⑩ build and the
duplicated `charge-states` fix both predate the hook and the resolver incident. Unclaimed work
allocation was live from the morning; it was simply written up last.

**What the structure actually is: one cause, three surfaces, discovered in the order that
instrumentation existed.**

| surface | had a ledger from | had a constraint from | so collisions here were |
|---|---|---|---|
| migration **numbers** | 13:35 | 15:31 | caught first, loudest, and got numbered |
| the **ledger file itself** | never | never | caught by accident, silently |
| **units of work** | 16:05, advisory only | never | caught by a `/tmp` collision, not by any ledger |

**The apparent progression is a measurement artifact.** We found number-collisions first because
numbers were the only thing instrumented. The true finding is the single line the registry
already had at 15:50 — *a shared machine plus an identifier that is not unique* — and the
three-stage arc was a narrative laid over it afterwards.

**The strongest evidence that the arc was retrofitted: the collision numbers themselves
collided.** Two sessions independently derived "the next collision number" from shared state and
both produced *"collision seven"* — one for the auto-resolver dedup, one for the `0089`
double-claim. A taxonomy whose own indices collide was appended to by whoever wrote last; it was
not derived from causal sequence.

**And the claim that "every correct fix made the identifier unique at the source" is false.**
Counting what was actually applied: **two genuine source fixes** (the pre-push hook's two checks;
absolute `PGDATA` in `harness.sh`) against **eight protocols** — the 0083 tiebreak, "never
auto-resolve this file", the named-decider rule, "name temp dirs after your session", the
in-flight claim table (*"Advisory — no hook can enforce this"*, by its own admission), "name the
tree", "claim the slice". Even the exemplar table below contains a naming convention dressed as
a constraint.

**The honest finding is better than the tidy one: the day produced two constraints and eight
protocols — and the protocols were written by the same sessions that had just finished
demonstrating that protocols fail under parallelism.** Where a source fix was identified but not
applied, that is recorded too: `0089`'s collision is *not* structurally invisible to the hook,
unlike the resolver's. One patch closes it — refuse a push introducing a row for a number already
rowed elsewhere. It was named and never written.

The three where a source fix *was* reached:

| collision | non-unique identifier | fix |
|---|---|---|
| numbers ×5 | "next free", computed per-session | claim row on origin + pre-push hook |
| `/tmp/dr85` | temp dir named after the *migration* | name it after the *session* |
| `pkill -f` | relative `-D` in the postgres command line | absolute `PGDATA` |
| duplicate work ×2 | no identifier at all for unnumbered work | an in-flight claim table |

## 3. Five artifacts that read as authoritative without being verified

This is the day's second class, and it is subtler than the first because **nothing looked wrong.**

1. **A build checklist that read well** — enumerated six properties of a two-party state machine;
   one was false (it claimed the machine self-heals a crash between stamp and effect; it detects
   and escalates). Written from a description rather than from the source.
2. **A suite at 475 green pins** that missed two blockers. The session's own post-mortem:
   *"both pins measured the symptom the design intended and stopped one question short."*
3. **A commit message asserting a property** — mine, claiming a grep returned nothing. I never
   ran it against trunk. It didn't.
4. **A code comment claiming a guarantee** that nothing enforced.
5. **A broadcast of "next free" from the coordinating session** — accurate when read, stale when
   sent, three times. Their own framing: *a number relayed by me is a stale cache carrying an
   announcer's authority, which is worse than no number, because it stops people checking.*
6. **This retrospective's own first version.** It asserted the three-stage arc as *"the sharpest
   predictive line the day produced"* without checking a single timestamp — in the document
   whose thesis is that well-formed narratives read as verified. Refuted within the hour by an
   adversarial pass. The correction is in §2.
7. **"Charging is off, verified."** The coordinating session verified the *code* — no migration
   assigns the flag, the guards return early on NULL — and then described the *world*. **Nobody
   has read the live row.** A session that tried got `[]` from an RLS-hidden table and correctly
   refused to count that as evidence. Their own naming of the pattern is the useful part:
   **"I verify the code and then describe the world."** That is the most transferable sentence
   in this document, because it is the failure that survives every mechanism listed above.
   ✅ **CLOSED the same evening.** `supabase db query --linked "select * from ops_flags"` returns
   one row with `payments_live_since` null. The conclusion was right all along — **and that is
   the uncomfortable part, not the comfortable one.** An inference that happens to be true is
   indistinguishable from an observation until someone looks, and this one went unlooked-at for
   a whole day precisely *because* it kept being restated confidently. The fix was not courage
   or a credential: it was one CLI flag nobody had tried (`--linked`, which runs as a login role
   and never meets RLS). **The gap between "we can't check this" and "nobody checked this" is
   where this class lives**, and every session that day landed on the first phrasing.

8. **This document's own §6 and its closing section.** *"`0085` is deployed but unreachable…
   the bug the slice exists to fix is still live in production"* — presented as the day's most
   uncomfortable fact, in the retro whose thesis is that well-formed claims read as verified.
   It was already false when written: both callers were in the live bundles by 17:18. **Two
   documents, five sessions, and a whole taxonomy of unverified-artifact classes, and the
   most-repeated operational claim of the day was one `supabase functions list` away** — never
   run, because the repo's silence about a deploy was read as the deploy's absence. **A deploy
   leaves no trace in git, so git's silence is not evidence about it.**

**The common structure: each artifact's FORM implies verification its CONTENT never underwent.**
A checklist implies someone checked. Green implies covered. A commit message implies done. None
of them were vague — vagueness gets questioned. **Precision without verification is
indistinguishable from precision with it**, which is why it travels further and lands harder.

**And every rule recorded today was broken by its own author within hours.** "Unpushed reserves
nothing" — by the session whose queue lived only in a conversation. "Verify, don't relay" — by me,
in a commit message, in the same hour I wrote the rule. "Numbers come from the file, never a
message" — by the announcer, three times. **That is not an argument against the rules. It is the
argument for mechanisms over discipline**, and it is why the pre-push hook is the most valuable
artifact of the day: it is the only one nobody can violate by being briefly confident.

## 4. The join nobody tests

The same structural bug appeared at four layers. In each, both sides were individually
well-tested and the *seam* was not, because each side's test replaced the other side with a fake.

| layer | what broke | why both sides stayed green |
|---|---|---|
| suite ↔ shipping path | a pin tested a helper; the code that ships calls something else | the helper genuinely works |
| TS ↔ SQL literal | a marker string duplicated across languages (`owner_cancel_late`) | each side asserted *its own* copy |
| client ↔ database | a column-grant migration didn't grant `SELECT` on `role`, which an `ON CONFLICT … SET role = EXCLUDED.role` arm needs | the grant was correct for every read; the *write path* consulted it |
| **deployed schema ↔ code** | `routes` — the app selected `status`/`town`/`trace_thumb`; production still had only the 0001 columns, so every route fetch returned `42703 column routes.status does not exist` | the harness applies the REPO's migrations to a fresh cluster and never touches the real DB, so 524/0 says nothing about production; `tsc` typed the rows from a hand-written interface both sides agreed on and neither had observed |
| **SQL predicate ↔ TS predicate** | `dispatch_due_charges()` vs `isDue()` — one rule written twice, live, still open | each side's suite names the OTHER side as its real pin |

**A FIFTH layer, found in the adversarial pass, still open, and the only one that is live money:**
`dispatch_due_charges()` (0080) and `isDue()` (`collect-charges/handler.ts`) are **one rule
written twice**, and 0080 says so in its own comment. Verified divergences on trunk today:

| fact | SQL | TypeScript |
|---|---|---|
| attempt cap | hardcoded `< 3` | `MAX_ATTEMPTS`, imported |
| unparseable `next_retry_at` | `::timestamptz` **raises** → outer handler returns 0 → **the batch is never woken** | deliberately treated as **due** ("the failure direction to prefer is one extra attempt") |
| the cross-reference binding them | points at `handler.ts:110` | `isDue` is at **152** — the comment has already drifted |

**Neither side can pin the other.** The SQL predicate returns 0 without exposing its count when
the vault is absent, and the local harness *is* that environment — so 116's own header concedes
the rule "has NO pin in this suite and cannot have one here… its real pin is the TS twin it must
agree with." The TS side is tested only against fakes. **Both sides explicitly defer to the
other.** That is the join nobody tests, with the deferral written down on both ends.

**The repair the repo converged on, and it generalises: don't synchronise the copies — delete the
duplication.** Let one side own the fact, and have the other **read it at test time and verify
against it, in both directions.** No shared constant, no cross-language import, and it works with
the existing fakes untouched. In use now for two contracts (the cancel-tier marker, the
notification routing key), each mutation-verified to redden from either side.

**What the technique CANNOT close, which matters more than what it can.** Its precondition is
that one side owns the fact **as a literal the other can textually verify against** — so it
closes disagreements about a *name* (an error code, a marker, a title, an argument list) and
nothing else. It closed layers 2 and 3. It cannot close layer 1 (no text comparison reveals
which function the handler actually calls — that was fixed by *removing the input*, so the
client's numbers stopped being a financial input at all), it cannot close layer 4 (**every
instance of the technique reads `supabase/migrations/` — the repo's belief about the schema,
which is exactly the side that was wrong**; a test reading migrations would have stayed green
throughout the outage), and it cannot close layer 5 (you cannot regex two implementations into
agreeing about a *function*; that needs one side computing the rule and the other calling it, or
a differential test over shared fixtures).

⚠ **Two of the technique's own five instances shipped with the bug the technique exists to
catch** — one sliced a migration to end-of-file and so demanded the handler map an error it can
never receive; one hardcoded a *filename* for a function that has been re-created four times.
Both were caught by their authors re-reading their own fresh work.

⚠ **And four of the five run only when a human remembers.** The commit gate requires `tsc` and
the RPC-contract check; `deno test` is not in it, and there is no CI. The strongest instance is
the least celebrated: `check-rpc-contracts.mjs` is the only one *inside* the gate.

⚠ **Its precondition is easy to lose:** it holds only while the owning side stays the *only* copy.
The moment the reading side caches the value in a constant — which looks like tidying and would
pass review, because hoisting a repeated string is normally correct — the test passes against the
copy and the join reopens. Both contract tests now carry a comment saying exactly that, because
**the test cannot defend its own premise.**

## 4-bis. A class the eight do not cover: a spec that was written, reviewed, and never built

Found by the route session's post-deploy smoke pass, minutes after the schema landed. **A
signed-in owner saw 0개 코스 while the database held 13.**

`profiles.district` and `routes.town` are different vocabularies, measured against production:

```
district = {null, 반포동, 성수, 뚝섬, 서울숲}
town     = {반포동, 성수동}
overlap  = {반포동}                      ← one value out of five
```

Three of five district values filter every course away. An owner in 성수 sees nothing, though
성수동 has courses.

**The plan had already specified the fix** — *"falling back to normalized `profiles.district`,
falling back to unfiltered + log"*. Written, reviewed, and simply not built. Their framing is the
class:

> **A spec can be right, written down, reviewed, and not built — and nothing notices, because the
> missing arm only fires in states the seed data never reaches.**

Green pins, green gates, correct plan, absent code. **No test could have caught it**, because
what was missing was the code, not a test — which distinguishes it from the joins-nobody-tests
family it otherwise resembles. And it was invisible for exactly as long as the schema was
undeployed: **the deploy did not cause this, it revealed it.**

**The detector is cheap: when a plan says "falling back to X", grep for X.**

**Second-order, and the third instance today:** the empty screen rendered *"**0개** 코스의 만남
장소는 정해져 있고…"* — a sentence asserting something about zero things. Copy that reads
correctly at n≥1 and lies at n=0 is a recurring shape in this codebase, not a one-off.

## 5. The one failure with no mechanical fix

⑫'s memo carried Sean's ruling in three places while its status line still read *"🟡 OPEN — needs
Sean's ruling."* The set's own convention is *read the status line, not the body* — which makes a
stale status line **the one artifact everybody trusts without checking.** A reader would have
concluded he owed an answer he had already given.

It was caught by another session reading it against the body. Not by a test, not by a failure.
The follow-up sweep of all thirteen memos then found two more saying *"Buildable"* long after
their code had shipped.

Every other class today got a guard. This one gets a habit: **when a memo changes, change line 3
first** — and record *ruled / built / deployed* as three separate facts, because only the third
tells anyone it is real for users.

## 3 things that worked

1. **Adversarial review, and the split is not what I first wrote.** My first version claimed
   *"not one was found by its author."* Counted properly across eleven instances: **6 self-caught,
   5 cross-session** — and the self-caught ones were faster (2 minutes, 4 minutes, 7 minutes from
   claim to catch). The real finding is the one below, not this one.
   **⚠ And the number that should anchor this document: of eleven instances, ZERO were caught by
   an automated gate.** Eight by a person reading, two by executing the artifact. Every gate that
   now exists was built *after* the miss it would have caught.
2. **Applying a lesson reflexively.** Twice, a session turned its own new rule on its own fresh
   work and found a defect within the hour. That is a higher yield than applying it outward.
3. **Refusing to decide.** Codex answered three ⑫ questions and explicitly declined the fourth.
   A build session refused to invent a points number Sean had not set. Both refusals saved work:
   his eventual answers were "reward was about tone" (no currency at all) and a work-gate that

## 3 things to improve

1. **The registry needs a third guard.** It covers file-vs-file and row-vs-row, and collision
   seven slipped through the gap between them. A pre-push check that a claimed row has a file
   *or* a stated intent would close it.
2. **Deployed-state drift is now the live gap.** With the schema in production, `ruled / built /
   deployed` are three facts and the memos track two. The sweep found status lines stale by hours;
   after a deploy they will go stale by days.
3. ✅ **DONE.** `payments_live_since` read live: **null**. The generalisation that outlives it:
   **this repo has no habit of querying production, and it shows in every document.** Deployed
   schema, deployed functions, and live flag values were each described from the repo all day.
   Two commands cover almost all of it — `supabase db query --linked "<sql>"` and
   `supabase functions list` / `functions download` — and neither appears in any runbook here.
   Put them in one.
4. **Session identity is invisible in git.** 193 commits, one author, five sessions. Attribution
   lives only in commit-message prose. A trailer naming the session would make every future retro
   sharper at zero cost.

## 3 habits for tomorrow

1. **Claim before you edit a shared surface** — path-keyed, with `exclusive` or `shared`. It cost
   ten seconds each time today and would have prevented two duplicated hours.
2. **When a claim is unanswerable, look for the stronger question that is answerable.** "Which
   client build is live?" had no local answer; "what has *every* build ever read?" did, and
   dissolved the question instead of answering it.
3. **Change line 3 first.** Status before substance, every time.
