Rules this lab is bound by — a variant that breaks one is unusable, not merely worse

  • Korean in the frames, English around them. Every string inside a phone frame is product copy; every heading, rationale and annotation is English (CLAUDE.md §Language).
  • No invented data. Where a frame shows a value, the binds line under it names the field. Exactly one variant (P③'s refund arm) needs something the client cannot read today — it carries NEEDS NEW SERVER DATA, and it is the only one. One more (P①) needs a new link in a file outside this cluster, and says so.
  • Tokens only. Zero new hexes. Two variants are purely a role correction between tokens that already exist (paper.line is the brand hairline, not a button face).
  • Type floor 14pt inside every frame. The only sub-14 text is the latin letterspaced kicker class and the device status bar.
  • One coral surface per frame, and Black Han Sans at most once.
  • Frozen surfaces: this cluster touches none of the DO-NOT-REFACTOR list — the fitness collapsing hero and the meetup stage machine are elsewhere. It does border one contract-ordered sequence; see the box below.

Two things in this cluster are load-bearing and no variant may touch them

① The cancel-fee ladder sentence (request.tsx:1237-1243). It reads 「시작 24시간 전까지는 취소 수수료가 없어요 — 이후에는 10%, 러너가 이동을 시작한 뒤에는 50%가 붙어요.」 and those two numbers are computed, not typed: Math.round(cancelPolicy.feeRate*100) and cancelPolicy.enrouteFeeRate*100 from src/store.ts:221-227, which mirrors the server ladder (0066/0085). Where this lab prints that sentence it prints the same computed values. Any variant that moves the sentence must keep it bound to cancelPolicy — a hardcoded percentage on the order screen is a legal statement the server can contradict the next time the ladder moves.
② The four steps after createBookingHold resolves (request.tsx:564-628) — ① bookingId first, ② recurring series, ③ nomination, ④ routing — are ordered by contract, and the comment says so ("순서가 계약이다"). Every request variant here is above that line: dock, copy, disclosure. None reorders it.

  3. Is 매치 % a claim we want to keep making (M②)? It is computed, not measured, and it silently renormalises for runners with no respond-rate data. The screen already discloses this in prose. Demoting it to a rank is more honest and less scannable. Sean's call.
  4. Should the 「러너 선택」 arm of matching.tsx exist at all? Nothing routes to it: fresh holds go to /owner/radar, and the only push is schedule.tsx's rebook.   6. Can we ask the server whether money was captured (P③)? The refund sentence is unconditionally 「환불이 진행 중이에요」, which the screen's own TODO says is wrong for uncaptured incidents. If that distinction is too fine for an owner in a hurry, the dot should be dropped rather than softened, because the failure mode is an owner who believes a day is open and finds an empty grid.
  8. Is the map-less spot list (N③) honest? It writes real coordinates for real named places, but the owner confirms a pickup point they never saw on a map. The alternative is the current dead end. I could not resolve this from the code — 0065's "pin is truth" doctrine was written for a world where the map loads.

I do not know at what distance a drift stops being normal (an apartment complex entrance is legitimately 200m from its registered address) and I did not want to invent a number. No variant here moves it, because moving it changes what the screen asks for, not how it looks. Flagging it as the next question after the ladder.
