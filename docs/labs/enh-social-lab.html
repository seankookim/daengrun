Lab note — not product copy

The LIGHT cell moves from paper.critical to paper.pending because it is now a caution with a sentence, not a failure — and critical is the loud-fail ink, which this is not. lighting = 'partial' and null get no sentence: 부분 is a shrug and null means unmeasured. Only the 'none' enum value earns a line.

Binds to
routes.lighting enum (none | partial | lit, 0078) and routes.shade (low | mid | high) — both already fetched, already used by the chip filters on the map screen. The shade sentence is optional and drawn only for high.
What this costs
No new server fields, no new routes. KOpen questions — I could not decide these from the code

  1. Detail-screen title grammar is still unspecified. §3b fixes the screen title at 30/900 Black Han Sans, but that spec was written for text-titled tab screens. In this cluster the pushed screens run 23/900 display (course, leaderboard), 23/900 plain ink (compose, runner-profile), 19/900 display (shot) and 30/900 display (community, alerts, cards, which are tab-ish). I① guesses that on a detail screen the subject gets the display face and the page label goes plain — is that the rule, or should every pushed screen carry 23/900 plain ink like report.tsx?
  2. Should the feed become 우리 동네 for real? A① fixes the lie by deleting the claim, but the claim is a good product idea and the data exists: routes.town is populated ('반포동') and profiles.district is a free-text field owners already fill. Making the sentence true means a filter on fetchFeed and a decision about what happens to a Banpo pilot user with an empty district. Delete the claim (A①) or build the filter?
  3. Does the leaderboard need to show 내 순위 — and may it? BoardRow is {name, photoUrl, km, runs} with no id, so the client literally cannot find you, and both variants refuse to guess by name. Adding a 「나」 flag means the definer RPC compares auth.uid() internally (safe, no id leaves the server) — but it also means an owner outside the top ten learns their exact rank, which is a product decision, not a technical one.
  4. Where does a safety alert land for an owner? E① routes kind='safety' to /club/session/[sid] because ref_id is a session id and that screen ships. For a club host that is obviously right. For the owner of a delegated dog receiving 「반환 지연 경보」, is the session screen the right destination, or /safety (안심 센터, which has the SOS and the emergency contacts), or the case screen /club/case/[cid] — which would need a case id we do not have in ref_id?
  5. Is a filled review star a gold-budget use? §8 reserves gold for milestone events. H① paints filled stars in colors.gold #D9A93C (today they are off-token #5a7a3c green, which is worse in a different way). Stars are gold everywhere on earth — exempt convention, budget spend, or should they be paper.pending amber / plain ink?
  6. Rating: scope the label or build the aggregate? H① prints 「최근 5개 평균 ★ 4.8」, which is exactly what the query returns. The alternative is a small server aggregate over all public reviews for that runner — cheap, but it is new server data and it changes what the number means on a page owners use to choose a stranger.
  7. Is runners.online allowed to say 「지금 활동 중」? It is a self-toggled boolean with no freshness column, so a runner who forgot to toggle off reads as online indefinitely. Options: keep the word (and accept the staleness), add a last_seen_at and derive it (new column), or delete the dot — a colour-only signal with no word is not defensible either way.
  8. May Instagram own the emphasis slot? G① gives the coral surface to 「인스타 스토리로 올리기」 because it is the single-tap destination and 공유가 곧 마케팅. It also means the loudest control on one of our screens sends people into someone else's app. The alternative (coral on 공유하기, Instagram as a third ghost) fixes the emphasis-budget violation just as well and is more conservative.
  9. Alerts: ceiling sentence or pagination? E② states 「최근 20건까지 보여요」 because the query is .limit(20) and silence is worse. A 「더 보기」 would need a cursor argument — small, but it is a new query shape and I did not draw a control I had not costed.
  10. 만남 장소 is deliberately not in this file, and that deserves a decision. The course briefing shows ◆ 만남 장소 as a map marker but never names it, even though routes.anchor_name / anchor_detail exist and are excellent copy (「세빛섬 매표소 앞 계단 아래」). The client cannot read them: routes_public (0110) names its columns explicitly and excludes every anchor column, and that select list is described in the migration as the only control standing between a caller and the base table. Publishing a physical meeting point is a privacy call plus a definer-view migration — an /autoplan job, not a lab variant. Worth doing?
  11. Chat: does anyone need 읽음? chat_messages has no read column, so a read receipt is new server data (and a product promise). D① deliberately adds day separators instead, which cost nothing. If handoff coordination is failing because a runner cannot tell whether the owner saw 「5분 늦어요」, that is the argument for the column — but it should be made from a real incident, not from a mock.
