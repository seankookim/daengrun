Twelve numbered enhancements across the three runner screens where the runner asks “what have I earned, what have I won, and where am I in the queue.” Money is the most dangerous place to draw a number, so this file carries a stricter rule than the other enhancement labs: every figure in every frame either names its real column, or is computed by compute_runner_payout (0101) from an illustrative booking and is labelled ILLUSTRATIVE with the arithmetic shown. Nothing is rounded into existence. Three things these screens say today are contradicted by the server, and each one is fixed by a numbered variant rather than by a new feature.

The money table every earnings frame in this file uses — real arithmetic, illustrative bookings

compute_runner_payout (0101 §A): base = 9,900 (RUNNER_COMP_BASE — not the owner's 7,900) · distance = round(actual_km × 3,000) · addon = sum(bookings.addons[].price) · owner-caused stop adds guarantee = max(0, round((planned_distance − distance) × 0.5)) · fee = round(gross × runners.commission_rate), once. Net is the caller's subtraction and is exactly what ledger_items stores column by column. Commission 0.33 (0059).

⚠ Three things these screens ship today that the server does not support

Measured while reading the three files and their server counterparts. None is a variant idea; each is a contradiction, and each is cheap.
  1. A ledger row prints the PLANNED distance beside ACTUAL-distance money. fetchLedger (api.ts:2605) maps km from bookings.km — the planned figure — and gates it on a runs row existing. But distance_pay was priced from runs.actual_km (0101 §A). A run stopped at 2 km on a 5 km plan therefore reads 「보리 · 5km · 실수령 13,668원」, and 13,668 is a 2 km payout. The fix is one column in a query that already runs: the runs lookup already selects booking_id — fetchRunnerWeekStats selects booking_id, actual_km from the same table for the same reason. → earnings ③
  2. 부스트 is a reward nothing reads. open-drop inserts a boosts row (+24 h) for pick_choice = boost. Grepping every migration and every edge function: the only consumers of boosts are fetchActiveBoostLabel (a display string) and 0115's deletion sweep — whose own comment calls it “a time-boxed visibility window”, a window no matching function implements (available_runners 0015, runners_available_for 0054, marketplace_open_requests 0042/0056 never mention it). shop.tsx prints 「매칭 부스트 활성」. A pick drop is irreversible and arrives once per ten completed runs, so a runner can burn it on a no-op. → rewards ②
  3. The empty state promises the wrong drop. rewards.tsx:82 computes cycle5 = totalRuns % 5 and says 「{5−cycle5}번 더 완주하면 보급 드랍이 도착해요」. settle_run_tx (0083 §6:812) mints a 픽 drop when the new total is a multiple of 10 and a mini only otherwise. A runner at 17 completed runs is told 보급 and will get 픽. → rewards ③
