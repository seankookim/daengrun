⚠ Three sentences these screens ship today that the server does not support

These are not variant ideas, they are measured contradictions found while reading the four files. Each one is fixed by a numbered variant below, and each is cheap.
  1. runner/home.tsx:~820 — the online toggle's offline sub-line, 「새 요청이 멈춰 있어요」. The open pool (marketplace_open_requests, 0042/0056) has no online predicate; its gate is is_active_runner(). Offline removes the runner from the owner's nomination lists (fetchCertifiedRunners, runners_available_for 0054 r.online = true) and from the find-now surfaces (available_runners 0015, count_available_runners 0003) — it does not stop open requests. → home ④
  2. runner/requests.tsx:432 — an applicant is told 「지금은 열린 요청이 없어요」. For a pre-certification runner a request can never arrive (is_active_runner() = tier <> 'applicant', 0004:4-10). Home already fixed exactly this lie for its own inbox; requests still tells it, and it already fetches fetchMyRunnerStatus() — it reads st.online and throws the tier away. → requests ①
  3. runner/calendar.tsx:174,191 — a completed ticket prints 「정산 완료」 and 「정산됨」. Home's week line deliberately says 「정산 예정」 because there is no code path that pays a runner yet; the ledger row means the run was priced, not paid. Two screens, one fact, two vocabularies. → calendar ③

OPEN QUESTIONS — things the code could not settle

  1. One mapper field, three variants. home ②, requests ② and requests ③ all need OpenRequest.scheduledAt. The column is already inside REQ_SELECT and inside the marketplace_open_requests column list, so this is a client-only change — but scripts/check-rpc-contracts.mjs may consider the view's shape a contract. Ship it as its own tiny slice first, or fold it into whichever variant is picked?
  2. What deadline is worth an amber chip? requests ② draws the amber 임박 chip on a 1-hour-out request and a quiet dim line on a 14-hour-out one. The cut point is a design decision I could not derive: the server has no urgency threshold at all — only scheduled_at < now(). Candidates: <2h (matches available_runners's own 2-hour horizon), <3h, or "today".
  3. Does the deadline sort move the coral? The coral rule reads directed[0]. If requests ② sorts each leg by deadline, the coral follows the soonest directed request rather than the server's return order. That is probably right (the soonest one is the one that expires first) — but it is a behaviour change riding on a display change, and it should be picked deliberately.
  4. Conflict warning vs. the coral ladder. requests ③ moves the coral to the topmost directed door without a conflict. If every directed request conflicts, does the coral go to a 근처 door (contradicting "근처 accepts are never coral"), or does the screen render zero coral (legal per R2c)? I drew zero-coral; confirm.
  5. Calendar's 20-row window. Grouping (calendar ①) makes the window visible rather than fixing it: fetchRunnerJobs is scheduled_at DESC limit 20, so a runner with many future bookings loses their past runs and vice versa. Home worked around it with a second query (fetchInFlightRunnerJobs, B9). Does calendar want the same treatment (a bounded past query), or is 「최근 20건 안에서」 an acceptable caption for the pilot?
  6. Is settlement ever knowable to the runner? calendar ③ changes 정산됨 → 정산 예정 because this screen cannot tell priced from paid. done.tsx reads runResult.settled, which proves the distinction exists somewhere. Should calendar fetch it, or is 정산 예정 the honest terminal word until a payout path exists at all?
  7. Should 하루 최대 러닝 have a floor? availability ③ lets a runner set it. Setting it to 1 silently removes them from most slots — legitimate, but it is supply we lose without a word. Warn at 1? Refuse below 1 only? Or leave it entirely to the runner (my instinct, since the whole point is that they already own this number)?
  8. 오늘 머리줄 (home ③) spends a fact twice. 오늘의 루트 already renders today's stops. Keep both (summary + detail) or drop the line? This is the only variant in the lab that trades against the 한 사실 한 번 rule, and I did not want to resolve it quietly.
  9. Request-ticket face size. home ② gives the front request a 40px avatar; the 진행 중 ticket's is 42px. Same size (they are twins) or deliberately one step down (the in-flight dog outranks a request nobody accepted)?
  10. The offline sentence's third clause. home ④ keeps 「확정된 러닝은 그대로」. Once the sentence names nomination lists explicitly, is that clause still earning its width at 14pt on a 390pt screen, or is it now obvious?
  11. Unmeasured, flagged rather than asserted: the availability stepper row may not fit. While rebuilding that row at 1:1 I got an arithmetic near-miss on a 390pt device — card content ≈ 390 − 30 gutter − 28 card padding − 2 border = 330, versus two steppers (46 + 46 + value + 24 each) plus the 8px gaps and the — separator ≈ 344. RN's flexShrink defaults to 0, so an overflow would clip rather than reflow. My Oswald advance-width estimate carries real error bars and I have no simulator here, so this is not a finding — it is a five-minute measurement someone should take before touching that screen. The lab frames tighten the stepper slightly so the mock reads correctly with a fallback font.
