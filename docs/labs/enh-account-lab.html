enhancement lab · 2026-08-24 · account + system cluster · new hexes 0 · 2 variants per screen

This cluster is the app's plumbing: the door (index, login), the two onboarding funnels, the identity hub (my), the two settings-adjacent screens (settings, payments), the safety centre, and the shop. None of them is where the product's peak lives — which is exactly why they accumulate stale sentences and retired tokens without anybody noticing. Every variant below came out of reading the file, not out of wanting the screen to look different: eleven of the eighteen fix something the code and the copy already disagree about. Nothing here invents a field, a route, or a colour.

What is real in these frames, and what is a placeholder

Real, and cited in every Bindings line: every field name, every server predicate, every status vocabulary, every measured contrast number, and the four point amounts (+50 완주 · +30 응가 · +200 골드 패치 · +500 코스 마스터 — the values settle_run_tx actually writes) and the stamp wall's fixed print order.
Placeholders, and nothing turns on them: person and dog names (선국 · 민준 · 초코 · 엄마), the profile id stem DH-4C81A20F, the handle @choco.runner, phone numbers, the point balance 1,280, the receipt amounts (22,900 / 16,900 / 0), the gear claim's item and milestone, and the addresses. Each of those sits in a slot whose binding is named — the number is a stand-in for a row, never a claim about one.
Lab annotation, never product copy: the pale grey #EEE-bordered blocks inside some frames, which describe a state that would occupy the same slot rather than a second element on the screen. Each is labelled where it appears.

A · 역할 선택 app/app/index.tsx

The first screen of the app, and the one nobody exercises end to end. A tap here fires four sequential network calls — profile read, UPDATE-or-INSERT, ensureRunner (runner only), and a first-run derivation (dogs count for owners, profiles.district for runners) — and every one of them can fail. Today all four report as one word, and every failure is an Alert.alert that disappears when dismissed. Structure (two full-bleed halves, coral divider) is not touched by either variant.

현재As it ships today

Reproduced including the cold-start window: while useAuth() is still resolving, notReady swaps both descriptions to 「시작하는 중...」 — so the first sentence a first-run user ever reads about the product is replaced, on both halves at once, by a status word. The screen has no Black Han Sans use at all (both names are 40/800 body).

OPEN QUESTIONS — things the code could not settle

  1. Who publishes 이용약관 / 개인정보처리방침, and when? login ① is honest because they are unpublished — but the privacy draft's own header lists three obligations that copy cannot fix: no destruction path for runs.trace (measured 2026-08-19: none of the 17 operational crons touches location), no 위치정보 이용·제공 확인자료 ledger table, and the KCC 위치기반서비스사업 filing. Those are Sean-only and legally load-bearing. Does login ① ship now as the interim, or does the whole thing wait for the published URLs? My instinct is ship now — the current sentence is worse than either end state.
  2. Does the shop keep a boutique voice at all? shop ① deletes six invented SKUs and four 준비 중 alerts. What it cannot decide is whether the preview was doing real marketing work. If it was, the honest replacement is one or two real products with a real supplier — which is a business task, not a design one. If it was not, ② is the cleaner end state and the tab should say 포인트.
  3. Should 로그아웃 and 역할 전환 live in two places? Both appear in 마이 and in 설정, with different paint in each (마이's signout carries a coral tick and an email sub-line; settings' is a coral-ink row). Neither variant resolves it because it is a product call about what 설정 is for. Related: if 설정 ② lands, the two screens' 로그아웃 rows will finally disagree on colour on purpose — worth a deliberate ruling.
  4. Is 「알림 종류별 설정」 the right pending promise? settings ① names per-kind preferences as the missing feature. There is no preferences table, so nothing constrains the shape — it could equally be «중요 알림만», or a quiet-hours window, or nothing at all (the OS switch may be enough for a pilot). Naming a specific unbuilt feature in a 준비 중 label is a promise; is that one we want to make?
  5. safety ①'s counterparty name costs one read — is it worth it? The cheaper version says only 「지금 진행 중인 러닝이 있어요 — 상대방에게 바로 알려요」 with no name, using only the two booking-id helpers. Naming 민준 makes the alarm concrete; it also puts a person's name on the most alarming card in the app. I drew the named version; the unnamed one is defensible.
  6. onboard/runner ①: which door is primary? I kept 시작하기 as the coral CTA and made 인증 신청 secondary — but the measured truth is that a runner who goes home cannot receive anything. If the funnel's real goal is applications, 인증 신청 should be the coral one. That is a conversion decision, not a layout one.
  7. Does the owner's push ask belong in onboarding at all? onboard/owner ① moves it there by analogy with the runner's location ask. The counter-argument is real: the owner has not yet booked anything, so «러너가 수락하면 알려드려요» describes a future they have not chosen — and the card-registration decision (docs/decisions/card-registration-placement.md) reasons exactly the opposite way about a different ask, placing it inline at first booking rather than in onboarding. Same question, and the two answers should be consistent.
  8. The card-register slice is blocked on Sean's Ⓐ lab pick and the agreed placement is «inline at first booking, plus one skippable soft prompt at the end of onboarding». That soft prompt does not exist in either onboarding screen today. It is out of this lab's scope (no register sheet to prompt toward), but the decision doc thinks it is coming — it should not be forgotten.
  9. my ②'s trade is genuinely two-sided. §3b retired latin section kickers app-wide, and 마이 is the screen where that grammar carries the most meaning (it is a passport). I drew the conforming version because the law is a law — but if the passport keeps its § heads by exception, that exception should be written into DESIGN.md rather than surviving as drift.
  10. Unmeasured, flagged rather than asserted. settings ② collapses the account card into hairline rows at gutter 15. On a 390pt device the 현재 모드 row's label + value fit easily, but I have no simulator here and 로그인 / 카카오 at 15.5pt with a long Kakao-supplied name could crowd. It is a five-minute check, not a finding — the lab frames use a fallback font and cannot settle it.
  11. Two screens ask for the same 이름 and neither knows the other did. onboard/runner writes profiles.name; 마이's sheet writes it again; index.tsx writes it a third time on first INSERT (from the email stem, or 사용자 for a Kakao account with no email). The measured bug that produced the current UPDATE-or-INSERT shape came from exactly this overlap. Nothing in this lab touches it, but the owner onboarding never asks for a name at all — so an owner is called 사용자 to their runner until they find 프로필 설정. Should 보호자 온보딩 ask for the owner's name? That is a third step, and I did not want to add one quietly.
