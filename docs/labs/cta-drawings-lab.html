the dot · overruled, then fixed

A pulsing dot is a promise. Let's make it a true one.

My objection was that a pulse means live elsewhere in the product. Your call stands — and there is a version where the objection disappears entirely: bind the dot to real availability. It pulses because runners genuinely are online near you right now, and the subline says how many.

✓Now it means exactly what it looks like. Live dot = live runners. Same vocabulary as the ● LIVE pill, used for the same reason, so nothing is borrowed.
✓It reports rather than nags. The count changes through the day; the dot is data, not decoration.
!The rule it buys: when zero runners are online, no dot and no pulse — the button stays, the promise doesn't. Honest empty, and it means the dot is trustworthy the rest of the time.

colour + drawings · one per job

Every button carries its own picture

Line drawings that bleed off the right edge, sitting behind the type at low opacity. Each is the thing the button leads to — radar rings for the radar, a route trace for the map, perforation for the ticket — so the picture is a preview, not an ornament. Grounds are the system's existing washes (goldSoft · voltFill · lilacInset · blueWash), which is why adding colour everywhere does not break "one coral per frame": only the primary is saturated.

rules that keep this from getting loud

Four

1 · One saturated fill per screen. Coral is the only solid; every other ground is a 95%-white wash. That is already the system's rule — this just uses more of it.
2 · The drawing is a preview, never decoration. If a button's picture doesn't depict where it goes, it doesn't get one.
3 · Drawings stay under 8% ink and always bleed off an edge, so they read as a watermark behind the type rather than an illustration competing with it. Text contrast is unaffected.
4 · The dot only pulses on real data. No runners online, no dot — see above.
